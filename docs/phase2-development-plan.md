# 猪猪产品毒舌官二期开发整体规划

> 版本：2026-07-23
> 面向用户：独立开发者
> 二期定位：从单次产品评审工具升级为“产品验证与决策工作台”

## 1. 二期目标

二期不以“生成更多、更长的 AI 内容”为目标，而是建立一条可持续复用、可追踪、可验证的产品决策流程：

```text
产品想法
  -> 初始评审与关键假设
  -> AI 桌面市场调研
  -> 用户真实验证任务
  -> 证据沉淀
  -> 继续 / 转向 / 暂停决策
  -> PRD、市场报告、路线图、PPT 等产物同步
  -> 后续跟踪与重新评估
```

核心价值不是替用户“问一次 AI”，而是帮助用户维护以下长期资产：

- 项目上下文和版本历史。
- 市场结论及其引用来源。
- 产品假设、未知问题和验证状态。
- 用户访谈、问卷、转化数据等真实证据。
- 每次产品决策的依据和影响范围。
- 由同一组事实生成、并能随决策同步更新的项目产物。

## 2. 当前项目基线

现有一期已经具备：

- Vue 3 + Vite + TypeScript + Pinia 前端。
- Spring Boot 3 + Java 17 + MyBatis Plus + MySQL 后端。
- DeepSeek / Mock Provider 路由和结构化评审输出。
- 评审详情、历史记录、Markdown 导出、开发任务包和分享卡片。
- `ideaGroupId`、`parentReviewId`、`versionNo` 组成的想法迭代链。
- 关键假设、未知问题、质量审计、多维评分和 Go/Pivot/Pause 决策字段。
- 基于 `X-Session-Id` 的匿名数据隔离。

当前关键限制：

- 没有正式账户、租户、订阅和权益系统。
- `ideaGroupId` 仍是评审分组标识，还不是完整的项目实体。
- 没有来源、证据、声明、调研任务和决策记录等独立数据模型。
- 没有联网研究工具层、引用抓取和来源可信度规则。
- AI 调用日志已预留 token 字段，但还不能形成可靠的成本核算。

## 3. 二期设计原则

1. 先做决策闭环，再做产物数量。
2. 先复用 `ideaGroupId` 验证项目工作台，再迁移到正式项目实体。
3. AI 生成的推断、公开资料和用户提供的真实证据必须分开展示。
4. 所有市场结论必须能追溯到来源；无法确认的信息明确标注未知。
5. 联网内容属于不可信输入，不能覆盖系统规则或直接触发高风险写操作。
6. 对话助手必须绑定当前项目、当前产物和可用证据，避免退化为通用聊天框。
7. 文档和 PPT 是证据与决策的下游产物，不应各自维护一套事实。
8. 先以单人项目和匿名会话完成内测，正式收费前必须完成账户和租户隔离。

## 4. 目标领域模型

二期最终建议形成以下核心对象：

| 对象 | 作用 | 关键关系 |
| --- | --- | --- |
| `ProductProject` | 独立开发者的一项产品计划 | 拥有版本、证据、决策、产物和任务 |
| `ProjectVersion` | 产品方向的一次版本快照 | 可关联现有 `review_records` |
| `ResearchTask` | 一次桌面调研或用户验证任务 | 产生来源和证据 |
| `Source` | 网页、报告、文件、访谈或数据集 | 保存出处、时间、类型和可信度 |
| `Evidence` | 支持或反对某项产品声明的证据 | 关联来源、假设和决策 |
| `Hypothesis` | 待验证的用户、痛点、渠道、价格等假设 | 由证据更新状态 |
| `DecisionRecord` | Continue / Pivot / Pause 决策快照 | 记录依据、风险和影响范围 |
| `Artifact` | PRD、市场报告、路线图、PPT、任务包 | 由项目事实和决策生成 |
| `UsageLedger` | 模型、搜索和文件生成消耗 | 支撑额度、成本和套餐控制 |

第一阶段不要立即创建全部表。应先通过项目工作台验证信息架构，再按使用闭环逐步落库。

## 5. 分阶段路线图

### 阶段 0：一期基线收口

目标：确保当前 AI 输出质量升级和测试处于可继续开发的状态。

主要工作：

- 处理当前工作区中尚未提交的 AI Provider、Prompt、Parser 和测试改动。
- 跑通后端测试、前端构建和 Mock 主流程。
- 固化一期 API、数据库和评审字段文档。

验收标准：

- 后端测试通过。
- 前端生产构建通过。
- Mock 模式可完成创建评审、查看详情、版本迭代和导出。

### 阶段 1：项目工作台 MVP

目标：把“一条评审记录”升级为“一个持续推进的产品项目”。

主要工作：

- 暂时复用 `ideaGroupId` 作为项目标识，不立即迁移数据库。
- 新增项目工作台聚合接口。
- 新增 `/projects/:groupId` 页面。
- 聚合最新决策、关键假设、未知问题、验证计划、质量状态和版本时间线。
- 从评审结果页、迭代页进入项目工作台。

明确不做：联网研究、证据录入、聊天窗口、PPT、登录、支付。

验收标准：用户能够从任意一条评审进入所属项目，并清楚看到“当前结论、为什么、还缺什么、下一步验证什么”。

### 阶段 2：项目、假设、证据和决策数据模型

目标：建立产品差异化的核心数据资产。

主要工作：

- 新增正式 `product_projects`，并制定 `ideaGroupId` 到项目的兼容迁移方案。
- 新增假设、来源、证据、决策记录和验证任务表。
- 支持手工录入访谈、问卷、转化数据、网页结论和文件摘要。
- 支持证据“支持 / 反对 / 中性”关系及可信度等级。
- 项目工作台展示证据覆盖率、冲突证据和待验证假设。

验收标准：不调用 AI，也能完整记录一条假设、两条相反证据和一次人工决策。

### 阶段 3：联网市场研究 Agent

目标：自动完成可追溯的公开市场与竞品桌面调研。

主要工作：

- 抽象搜索和网页读取 Provider，避免绑定单一供应商。
- 设计研究计划、来源白名单/黑名单、检索、摘要、引用和失败处理契约。
- 输出市场概览、目标用户、替代方案、竞品矩阵、价格、渠道、风险和待验证问题。
- 每条关键结论关联来源 URL、标题、发布日期、抓取时间和摘要。
- 用户可以在执行前调整研究范围，在完成后接受或驳回证据。

安全要求：

- 网页内容只作为数据，不作为系统指令。
- 防止提示词注入、SSRF、超大响应、恶意文件和敏感信息写入日志。
- 不绕过付费墙，不把第三方报告全文当作自有内容存储或分发。

验收标准：给定一个产品项目，可生成至少包含可访问引用、竞品矩阵和未知项的研究结果；来源不可用时明确失败，不编造引用。

### 阶段 4：证据驱动的重新评估闭环

目标：让新证据真正改变决策，而不只是增加一篇报告。

主要工作：

- 用户上传或录入真实调研结果。
- 系统比较旧假设与新证据，生成变更说明。
- 重新计算置信度、优先级和 Go/Pivot/Pause 建议。
- 创建不可覆盖的决策版本，保留人工最终确认。
- 标记受影响的 MVP 范围、成功指标、路线图和项目产物。

验收标准：新增一条反对核心需求的高可信证据后，系统能说明影响了哪项假设、为什么建议转向，以及哪些产物需要更新。

### 阶段 5：产物中心与上下文助手

目标：基于同一份项目事实生成真实工作产物。

首批产物：

- 市场调研报告。
- 产品立项文档。
- 精简 PRD。
- MVP 路线图。
- 项目汇报 PPT。
- Codex 开发任务包。

上下文助手要求：

- 绑定当前项目、当前产物和选中证据。
- 支持修改受众、模板、语气、篇幅和视觉风格。
- 区分内容修改与样式修改。
- 不允许在没有证据的情况下悄悄改写事实。
- 每次生成保留模板版本、引用和项目版本。

验收标准：修改一次项目决策后，系统能提示哪些产物过期，并按用户确认重新生成。

### 阶段 6：持续跟踪与市场监控

目标：把一次性项目分析变成持续服务。

主要工作：

- 里程碑、验证任务、截止时间和状态。
- 定期竞品、价格、产品发布和行业变化监控。
- 变化摘要与原始来源对照。
- 只有达到阈值的变化才触发重新评估建议。
- 所有自动更新由用户确认后进入正式证据库。

验收标准：系统发现一项明确的竞品价格变化后，能通知用户、展示来源并建议是否更新原有决策。

### 阶段 7：账户、订阅和成本控制

目标：具备公开收费条件。

主要工作：

- 正式登录、用户身份和租户级资源隔离。
- 免费版、Pro 权益和额度控制。
- `UsageLedger` 记录模型、搜索、文件生成和重试成本。
- 月度额度、超额购买、幂等支付回调和订单审计。
- 隐私政策、数据删除、导出和保留期限。

建议首发套餐：

- 免费版：每月 3 次基础评审，不含深度研究。
- 创始 Pro：49 元/月，验证后调整到 69 元/月。
- Pro 内含有限数量的标准分析、深度研究、活跃项目和产物生成额度。
- 高成本任务必须按额度计数，不提供真正无限使用。

成本门槛：月度可变成本建议不超过实收收入的 25%。

### 阶段 8：评估、安全、发布和运营

目标：形成可稳定迭代的生产系统。

主要工作：

- 建立市场研究、引用、证据归因、决策一致性和产物同步测试集。
- 记录 Provider、模型、Prompt 版本、token、延迟、失败和回退情况。
- 增加限流、超时、熔断、重试、脱敏和审计。
- 建立灰度发布、回滚、数据迁移和成本告警流程。
- 跟踪激活、研究完成率、证据录入率、决策更新率、产物导出率和续费率。

## 6. 推荐开发顺序与依赖

```text
一期基线收口
  -> 项目工作台 MVP
  -> 证据/假设/决策模型
  -> 联网研究 Agent
  -> 证据驱动重新评估
  -> 产物中心与上下文助手
  -> 持续跟踪
  -> 账户、订阅与正式收费
  -> 生产评估与运营优化
```

账户和订阅可以延后实现，但从阶段 2 开始，所有新表和查询都必须预留用户/租户归属，并继续严格按当前 session 隔离，避免以后出现跨用户数据迁移困难。

## 7. 建议里程碑

以单人开发并使用 Codex 辅助为参考：

| 里程碑 | 建议范围 | 结果 |
| --- | --- | --- |
| M1 | 阶段 0-1 | 从报告工具升级为可见的项目工作台 |
| M2 | 阶段 2 | 可以手工维护假设、证据和决策 |
| M3 | 阶段 3-4 | 形成联网调研到决策更新的差异化闭环 |
| M4 | 阶段 5 | 生成可追溯的文档和 PPT，具备明显高级能力 |
| M5 | 阶段 6-7 | 持续服务、登录、额度和付费内测 |
| M6 | 阶段 8 | 可控成本下的公开 Beta |

不要用固定工期代替验收。每个里程碑通过后，再生成下一阶段 Codex 提示词。

## 8. 二期北极星指标

建议北极星指标：

> 每周完成一次“新证据进入 -> 决策或产物发生有效更新”的活跃项目数。

配套指标：

- 新建项目后完成首轮评审的比例。
- 完成首轮市场调研的比例。
- 至少录入一条真实用户证据的项目比例。
- 新证据触发决策更新的比例。
- PRD/PPT/报告导出率。
- 7 日和 30 日项目回访率。
- 单个活跃付费用户的月度可变成本。
